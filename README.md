# Agent 会诊室 · agent-clinic

> 记录工具告诉你**这一次**发生了什么。
> 这里回答另外三个问题：**你的 Agent 到底得了什么病、占几成、最短的复现路径是什么。**

在线体验：https://agent-clinic.app.workbuddy.host/?sharecode=HRSKWOV2YB

---

## 先用一句话说清它是什么

**把任意来源的 Agent 轨迹丢进去，它给你三样东西：**
**分叉点（错在第几步）、失败模式（这些错分几类）、最小复现用例（能直接进回归集的最短路径）。**

它不接 SDK、不做平台、不替换任何 trace 工具 —— 你把已有的轨迹丢进来就行。

---

## 为什么做这个

LangSmith / Langfuse 这类工具已经把「记录」做到了极致：span 树、token、耗时、输入输出，应有尽有。
但真实调 Agent 的人都有同一个体感 —— **打开一条 40 步的 trace，你还是得自己一行行读完才能知道错在哪**。

它们回答的是 L1「记录」和 L2「展示」。下面三层是空的：

| 层 | 问题 | 主流 trace 工具 | 本项目 |
|---|---|---|---|
| L1 记录 | 发生了什么 | ✅ 做得好 | **不做**，只做兼容接入 |
| L2 展示 | 树形时间线 | ✅ 有 | 只占很小一部分 |
| **L3 诊断** | **这一次为什么错、错在哪一步** | ❌ 要人读完 | ✅ 11 类归因规则 |
| **L4 归纳** | **这批失败分几类、各占多少** | ❌ eval 要自己写 | ✅ 签名聚类 |
| **L5 沉淀** | **能否缩成可复跑的最小用例** | ❌ 数据集要自己备 | ✅ 结构最小化 → 回归集 → 验收 |

本项目只做 L3–L5，但**入口向 L1 完全敞开**：OTLP、OpenAI、LangSmith、原生四种格式都能进。

---

## 它实际给出了什么

基于本仓库内 **48 条真实轨迹**（12 个任务 × 2 个 prompt 版本 × 2 次重复，模型 `deepseek-v4-flash`），
报告给出了一个我没预料到、但数据确凿的结论：

```
总失败率：v1 62.5%  →  v2 50.0%       （看起来修复生效了）
  修好了：只问不做     4 → 0
          没有动作     2 → 0
  弄坏了：过度转人工   6 → 9           ← 只看总分会把这件事完全藏起来
```

v2 补上了「什么情况必须转人工」的规程，于是 v1 那批「把执行变成反问」的问题消失了；
但因为它**只写了什么时候要转人工，没写什么时候可以直接办**，Agent 学会了过度保守 ——
一批本来一键就能退的订单被推给了人工。

**两条独立路径都指向同一件事**：报告里的「修复的代价」按失败类型比对，
「逐项体检」按评分器比对，两者互不相干却同时把「转人工策略」标成了退化项。
一条路径的结论可能是规则写巧了，两条路径撞在一起才算证据。

## 九个能力

### 1. 分叉点定位（L3）

同一条任务，成功轨迹与失败轨迹逐决策对齐（LCS），指出第一条走岔的决策。

```
            成功 T02-v1-1                        失败 T02-v1-2
第 1 步   get_order(order_id="A1025")     ←→   get_order(order_id="A1025")
第 2 步   search_policy(query="未发货…")  ←→   search_policy(query="未发货…")
...
第 5 步   refund_order(order_id=…, amount=469)   escalate(summary="用户要求…")   ← 分叉
```

### 2. 失败模式归纳（L4）

每次失败算一个签名（性质 + 首个出错工具 + 归一化后的证据），按签名聚类。
**只有 1 条样本的碎片会被合并成「零散异常」**，不允许出现「8 类失败里 6 类各 1 次」这种自欺欺人的报告。

能识别的 11 类性质：

| 性质 | 含义 |
|---|---|
| `tool_error` | 工具抛错 / 业务拒绝，且没有重试恢复 |
| `bad_argument` | 参数缺失、类型错、取值非法 |
| `over_escalation` | 本可自动完成，却甩给人工 |
| `escalation_missed` | 该转人工却自行处理 |
| `asked_instead_of_acted` | 信息已齐备，却把执行变成了反问 |
| `promised_but_not_done` | 声称已办理，实际没有任何对应调用 |
| `hallucinated_fact` | 结论里的订单号/日期在整条轨迹中不存在 |
| `loop` | 三步内以相同参数重复同一动作 |
| `context_lost` | 被别的动作打断后又用相同参数重查 |
| `no_action` | 整条轨迹没有产生任何有效动作 |
| `unknown` | **判不出来就写判不出来**，不编理由 |

### 3. 最小复现用例（L5）

这一步是差异化最大的地方。一条 11 步的失败轨迹，真正致因的往往只有 5 步。

做法是**依赖分析**而不是猜：从诊断指认的那一步出发，
- 反向追溯它用到的标识符（订单号、日期）是前面哪一步的返回给的 → `required_context`
- 正向标记被它牵连的后续步骤 → `consequence`
- 剩下那些「返回值从未进入任何后续调用参数」的步骤 → `droppable`，附上具体理由

产物是一份可以存进回归集的 JSON 用例。

**必须说清楚的一条硬线**：这是**结构最小化**，靠依赖推断，成本为零，但**没有重跑验证**。
输出里 `verified_by_replay` 永远是 `false`，界面上每一处都原样标注「未经重放验证」。
用未验证的最小化冒充验证过的最小化，是这个项目最不该犯的错。

还有一个反直觉但正确的结论：**任务级失败（只问不做 / 没有动作）会把最小化压到 1 步**。
这不是算法失灵 —— 它们本来就**没有出错的那一步**，病在缺一条指令。系统会明确标成
`terminal_only` 并解释清楚，而不是显示成一个可疑的「1 步」。

### 4. 回归验收（把 L5 真正闭上）

只做「最小化 + 存进回归集」是不够的 —— 那只是准备好了考卷。
真正有用的是**改完 prompt 之后，这批考卷还过不过**。

把新一批轨迹传进来（或直接用仓库内的），系统逐条回答：

| 判定 | 含义 |
|---|---|
| `fixed` 已修复 | 同任务的轨迹全部成功，且不再命中该病 |
| `partial` 不稳定 | N 条里还有 K 条命中 —— **时好时坏不算修好**，它只是把确定问题变成概率问题 |
| `present` 仍存在 | 全部仍命中，修复没有生效 |
| `changed` 变成了别的病 | 这个病不见了，但换成了另一个 —— 对应「修 A 弄坏 B」 |
| `uncovered` 未覆盖 | 这批里没有同一任务。**不算通过**，没考和考过了是两件事 |

任务匹配**只按 task_id**，不退回按 prompt 模糊匹配 ——
prompt 撞了不代表同一个任务，用模糊匹配会把「没考到」伪装成「考过了」。

### 5. 规则草稿（从诊断到能直接用的那句话）

每个失败模式除了「往哪个方向改」，还给一条**可直接粘贴进 system prompt 的条款草稿**：

```
过度转人工 →
以下情形必须直接办理，不得转人工：在受理期限内、金额未超上限、订单归属校验通过。
```

诊断到这一步才算闭环 —— 否则用户看完报告，还是得自己把建议翻译成 prompt。

### 6. 规则评分器（对标 LangSmith 的 evaluator）

7 个开箱即用的评分器，每个都输出**通过/不通过 + 一句人话说清为什么**：

`任务完成` · `参数卫生` · `结论有据` · `无空转` · `转人工策略` · `错误恢复` · `执行效率`

三条设计约束：

- **判不了就 skip，不硬给分。** 没有任务期望时，「任务完成」返回 `None` 而不是 1.0。
- **只有 0 / 0.5 / 1 三档。** 轨迹质量不是连续可微的，给 0.73 分是假装精确。
- **总分是加权，不是平均。** 任务完成权重 3.0，执行效率 0.5 —— 「省了 token 但没办成事」不该拿高分。
- **导入轨迹会标 `scope: tool_only`**。因为没有期望时最重的两项不参与打分，总分天然偏高；
  不标出来，1.0 看起来像满分，实际是没考。

### 7. 通用接入（这才是「工具」变「平台」的地方）

| 格式 | 典型来源 |
|---|---|
| `otlp` | OpenTelemetry / OTLP traces JSON（GenAI 语义约定）—— LangChain、OpenAI Agents SDK、LlamaIndex 等一大批框架 |
| `openai` | OpenAI Chat Completions 的 messages 序列（含 `tool_calls` / `role: tool`） |
| `langsmith` | LangSmith 运行导出（树形 `child_runs` 或扁平 `parent_run_id` 数组） |
| `native` | 本项目的轨迹格式，支持单条、数组、`{"runs": [...]}`、JSONL |

自动识别格式，认不出来就明确报错，**不硬套**。

接入层最容易被做假的地方，我全部反向处理了：

- **工具全绿 ≠ 任务完成。** OTLP 和 LangSmith 只告诉你「工具有没有报错」，
  不告诉你「任务有没有办成」。所以这类导入会被标 `success_known: false`、
  诊断结论为「未判定」——**不把不确定冒充成通过**。
- **LangSmith 扁平数组必须顺 `parent_run_id` 爬根分组。** 我第一版没做，
  结果每条 run 都自成一棵「树」，13 条本该是 3 条的轨迹。
- **样例是从真轨迹转出来的**（`tools/make_samples.py`），不是手写的。
  这样 roundtrip 测试才能验证「格式适配有没有丢信息」，而不是验证「解析器能读我的想象」。
- **接诊无状态。** 解析完立即返回，不落库、不外传。只有用户主动点「存进回归集」才写盘。

### 8. 逐任务实验对账（失败率的下半句）

版本汇总只给你两行数字：v1 失败率 62.5%，v2 50%。这行数字看起来像好消息，
但它把三件性质完全不同的事压在了一起：**有的任务被修好了，有的被弄坏了，
还有的从「稳定失败」变成了「一半概率失败」**。

所以这里按任务摊开，保留每格「通过几次 / 共几次」，不压成 0/1：

```
任务    v1      v2      判定
T04    2/2  →  0/2     弄坏了
T02    0/2  →  1/2     变好了，但不稳
T01    0/2  →  2/2     修好了
T08    0/2  →  0/2     一直坏着
```

本项目的真实数据读出来是这样一句话：

> 失败率从 62.5% 降到 50.0%。这 12.5 个百分点里，只有 **1 个任务**（T01）被真正修好；
> **4 个任务**（T02/T06/T07/T10）从「每次都失败」变成了「一半概率失败」；
> 同时**弄坏了 1 个**本来稳定通过的任务（T04）。
> 抛硬币任务从 1 个增加到 4 个 —— 失败率降了，不确定性反而涨了。

矩阵只告诉你「哪个任务坏了」。点开任意一行，还能把这两版的轨迹**逐决策并排对齐**：

```
v1 · T04-v1-1 · 成功                    v2 · T04-v2-1 · 过度转人工
get_order(order_id)              =      get_order(order_id)
get_user(user_id)                ◀      —
search_policy(query)             =      search_policy(query)
refund_order(order_id, amount…)  ◀      —
—                                ▶      get_user(user_id)
—                                ▶      escalate(summary)
「已全额退款 329 元」             =      「已为您转接人工客服，工单号 H9205」
```

这就是「弄坏了」的具体机制：v2 把「直接退款」换成了「查用户 → 转人工」。

三个刻意的口径：

- **只有「从没全过 → 全过」才叫修好。** 一半过一次不过，标「变好了，但不稳」。
  确定的问题可以排期修，随机的问题没法排期，只能被反复重新发现。
- **单版本稳定性单独统计**（稳定通过 / 抛硬币 / 稳定失败）。这一项只看版本自己，
  失败率完全看不见它。
- **病种迁移单独列。** 两版都失败但死因换了的任务会被拎出来 ——
  T06 从「没有动作」、T10 从「只问不做」，在 v2 里都变成了「说了却没做」。
  这不是修复，这是把失败换成了更难被发现的那一种。

### 9. 复核队列（机器判不准的，不直接进结论）

规则式归因给出的是**证据强度**，不是**正确概率**。置信度 0.70 和 0.85 的诊断在报告里
长得一模一样，但前者可能只是证据刚够写下来。多数工具的处理方式是：不处理。

这里主动把它们挑出来，每条都写明**为什么可疑**：

| 信号 | 触发条件 |
|---|---|
| `low_confidence` | 置信度 ≤ 0.70，规则证据刚够 |
| `unclassified` | 规则没认出来，只能记「未归类」 |
| `unstable_pair` | 同任务同版本跑两次结果不同 —— 这条轨迹代表不了该任务 |
| `expectation_missing` | 缺任务期望，只能判工具层 |

本项目的 48 条轨迹里，**27 条失败诊断只有 7 条进了队列（26%）**。
筛不动的队列等于没有队列 —— 所以「有点意思的疑点」被降级成附注，
不触发进队。

人可以三种动作，**分量各不相同，统计时分开计**：

- **确认** —— 机器判定成立。不改动任何分布，这是刻意的：签字确认不该被算成一次「动作」。
- **改判** —— 换成另一种病。**必须写理由**，因为它是唯一会改写结论的动作。
- **驳回** —— 判为不算失败（例如任务期望本身写错了）。失败总数减一。

界面上永远是「机器判定 N 条 → 人工复核后 M 条」两列并排，
**没签字的诊断照常展示，但不和签过字的混在一起计数**。

这是「会诊室」这个隐喻唯一说得通的做法：主治医师出报告，主任签字才算数。
没签字的报告不是废纸，但它还不是结论。

## 数据是真的，而且可复查

```
被测对象  一个只有 6 个工具的 ReAct Agent（订单/用户/物流/政策检索/退款/转人工）
业务环境  确定性假业务系统：12 笔订单、8 个用户、6 条售后政策
运行方式  在浏览器里真实调用模型，每一步的决策、参数、观测、耗时、token 完整落盘
模型调用  走平台的无密钥通道（WorkBuddy 云服务 LLM API），不需要任何 API Key
分析      全部离线完成 —— 运行时打开报告不需要模型、不需要网络、不会花钱
```

- **没有埋 bug。** 失败只来自模型的决策本身，不来自我写死的错误。
- 判定「成功/失败」看的是**工具调用是否匹配预期动作与金额**，不是模型的自述 ——
  模型说「已为您办理」不算数，得看有没有真的调 `refund_order`。
- 想验证：打开 `/lab/collect.html`，自己跑一批，再跑 `analysis/build_report.py`。

## 技术栈

```
后端   Python 3.11+ / FastAPI / uvicorn     （单一端口，同时托管前端与此 API）
前端   Vue 3 + TypeScript + Vite            （5 个路由、手写 40 行 hash 路由，零额外依赖）
诊断   analysis/  纯函数库，32 个单测
采集   server/static/lab/  浏览器端 ReAct 循环，SDK 本地托管（不依赖 CDN）
发布   WorkBuddy Sites（Python HTTP 服务）
```

运行时零外部依赖：不需要数据库、不需要 Redis、不需要模型密钥。

`analysis/` 的模块边界：

```
trace.py      轨迹模型（唯一事实来源，分析层不回头问模型）
diagnose.py   11 类归因规则，判不出来返回 unknown
align.py      LCS 双路径对齐
cluster.py    签名聚合成失败模式 + 可粘贴的规则草稿
minimize.py   因果链最小化 → 最小复现用例
evaluate.py   7 个规则评分器
ingest.py     4 种外部格式归一化
regress.py    回归验收：这批用例还过不过
build_report.py  把以上编译成一份静态快照
```

## 这份报告不声称什么

- 它只解释**已有轨迹**，不会替你重跑模型。要验证修复，就再采一批。
- **最小复现是结构推断，未经重放验证。** 要拿到 replay-verified 的用例，需要把 case 放回运行器重跑。
- 归因是规则式的，「置信度」是规则的证据强度，不是统计概率。
- 导入的轨迹若不含任务期望，任务级归因（该不该退款、该不该转人工）自动降级为「未判定」。
  系统不会替你猜任务要求什么。
- 样本 48 条。低于 30 条时，占比只应看趋势，不应当结论。
- 目前只覆盖「工具调用型 Agent」；纯对话型 Agent 的失败归因不在范围内。
- 实验矩阵与复核队列都是**单机单文件**实现（`data/reviews.json` + `data/regression.json`），
  没有多用户、没有并发锁。它够用在一台机器上给一个人看结论，不够做团队协作。
