# 01 · 设计决策与取舍

这份文档记录「为什么这么做」，尤其是**被我否掉的那些做法**。
一个项目能讲清自己放弃了什么，比它声称能做什么更有信息量。

---

## 1. 只做 L3–L5，不碰 L1

trace 领域已经被 LangSmith / Langfuse 做到了极致：span 树、token 统计、耗时、输入输出，还能接几十种框架。

再做一遍 L1 是纯粹的浪费。所以本项目的定位是：

```
L1 记录  → 不做，但入口完全敞开（4 种格式都能进）
L2 展示  → 只做最小必要（时间线 + 角色标注）
L3 诊断  → 核心：错在第几步、为什么
L4 归纳  → 核心：这些错分几类、各占几成
L5 沉淀  → 核心：压成用例、存进回归集、改完再验收
```

**代价**：没有 SDK、没有实时采集、没有多租户。想要这些的人应该用 LangSmith，然后把导出丢进来。

---

## 2. 用规则，不用模型

归因完全由可读的 if/else 规则完成，一次模型调用都不做。

**为什么**：

| 维度 | 规则 | 模型 |
|---|---|---|
| 可追溯 | 每条结论都能指到「第几步的哪个字段」 | 只能给一段解释，无法保证是同一件事 |
| 确定性 | 同一份轨迹永远同一份结论 | 每次可能不同 |
| 成本 | 零 | 每次诊断都要烧 token |
| 离线 | 报告是静态快照，打开就有 | 必须有网 |

**代价**：规则覆盖不到的情况会落进 `unknown`。
项目里 48 条真实轨迹中有 27 条失败，其中 0 条落进 `unknown` —— 但这是因为我先看了数据再写规则，
不是我预设了所有情况。**换一个业务域，`unknown` 的比例一定会上升**，这是规则派的固有成本。

**明确不做的事**：不用模型做归因，也不用模型给归因结果「润色」。
一旦引入模型，`confidence` 这个字段就失去意义了。

---

## 3. 判不出来就写判不出来

这是整个项目最固执的一条。

- 诊断的 11 类性质里，`unknown` 是一个**正常返回值**，不是错误。
- 评分器的 7 项里，判不了的返回 `None`（界面显示「跳过」），而不是给个中间分。
- 接入的轨迹如果缺任务期望，任务级归因直接**降级为「未判定」**，不猜。
- 回归验收里「这批没覆盖到」单列一类，**不计入通过**。

**为什么值得坚持**：诊断工具最坏的失败方式不是漏报，而是**编一个听起来合理的理由**。
用户信了，就去改错误的地方，比不给结论更糟。

**代价**：报告里会有一些「未判定」，看起来不如「全部识别成功」漂亮。
我认这个不漂亮。

---

## 4. 最小化不做重跑验证

轨迹最小化有两条路：

| | 结构最小化（本项目） | 重放验证最小化 |
|---|---|---|
| 做法 | 分析参数与观测之间的依赖，推断哪些步骤必要 | 逐步删除步骤后真重跑，确认仍然失败 |
| 成本 | 零 | 每个 case 要重跑 N 次，烧 token、耗时 |
| 结论强度 | 推断 | 事实 |

我选结构最小化，理由不是省钱，而是：**重放验证要求能重跑，而绝大多数用户拿到的轨迹是不可重放的**
（工具连的是他们的内部系统，我这边没有）。

所以输出里 `verified_by_replay` 恒为 `false`，`method` 恒为 `structural`，
界面上每一处都写「未经重放验证」。**用未验证的结果冒充验证过的，是这个项目最不该犯的错。**

如果用户自己有运行器，`case` 字段就是为这个准备的 —— 拿去重跑，然后把结果贴回来。

---

## 5. 零依赖运行时

服务端不需要数据库、Redis、模型密钥；前端不用 UI 框架、不引 vue-router。

**为什么**：
- 发布成公开链接给人体验，稳定性优先于工程化正确。少一个依赖，少一个半夜挂掉的理由。
- 48 条轨迹、5 个视图、40 行手写路由 —— 这个规模引框架的收益是负的。
- 评委/用户能直接读源码验证它不是套壳。`analysis/` 是纯函数库，可以单独跑单测。

**代价**：没有 ORM、没有缓存层、没有组件库。
如果轨迹量到十万条，这套东西就得重写存储层 —— 现在不需要。

---

## 6. 无状态接诊

`POST /api/intake` 解析完立即返回，**不落库、不留存**。

**为什么**：陌生人的轨迹可能含业务数据、内部字段、用户信息。
一个诊断工具没有资格把这些东西留在自己服务器上。

只有用户主动点「存进回归集」，才会写入 `data/regression.json`，而且存的是**最小化之后的用例**
（只保留因果链上的步骤，无关的查询已被剔除）。

---

## 7. 评分与归因刻意解耦

「修复的代价」按失败类型比对，「逐项体检」按评分器比对。两条路径的输入相同，但逻辑完全独立。

**为什么**：一条路径的结论可能是规则写巧了。两条互不相干的路径撞到同一个结论上，才算证据。

实际效果：诊断规则算出「过度转人工 6→9」，评分器算出「转人工策略 0.667→0.583」——
两边都在说同一件事，参考价值完全不同。

---

## 8. 明确的边界（我知道的短板）

1. **只覆盖工具调用型 Agent**。纯对话型 Agent 的失败（答非所问、态度问题）不在归因范围内。
2. **规则是为电商售后场景写的**。换到客服工单、运维排障、编码 Agent，规则要重写一大半。
3. **样本 48 条**。低于 30 条时占比只应看趋势，不当结论。报告里写了这句。
4. **聚类是签名匹配，不是语义聚类**。归一到同一签名的失败会被合并，措辞差异大的同类失败会被拆开。
   碎片合并机制能兜住一部分，但兜不住全部。
5. **`confidence` 是规则证据强度，不是概率**。0.85 不表示「85% 的可能性是这个病」。
6. **不做多轮会话**。一条轨迹 = 一个任务，跨会话的上下文丢失不在范围内。
