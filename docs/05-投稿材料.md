## 三、作品说明

### 它解决什么

Agent 上线之后，团队手里有一堆 trace，但没人能回答三个问题：

1. **这次的失败，和上次那次，是同一个病吗？**
2. **改完 prompt 之后，是修好了，还是换了个死法？**
3. **这份诊断里，哪几条我能直接拿去改线上系统，哪几条只是猜的？**

LangSmith / Langfuse 这类工具解决的是「记录」和「看板」。它们能让你回放任意一次调用，
但不回答上面三个问题 —— 因为它们只做 L1（记录）和 L2（展示），
不做 L3（诊断）、L4（归纳）、L5（沉淀）。

会诊室只做 L3–L5，并且把入口向 L1 完全敞开（四种轨迹格式任意导入）。

### 创意与场景（对应评分项 35 分）

**做的不是又一个 trace 查看器，是「归因」这件事本身。**

四个别人不做的判断：

**① 早发生的小错才是根因。** 排序规则是 `(步号, -严重度)` 而不是按严重度：
第 2 步参数传错 → 工具报错 → 第 3 步模型开始编造 → 最终答复幻觉。
按严重度排会指向最后的幻觉，但你改它没用；按步号排指向第 2 步，改一个参数，后面全好了。

**② 失败率是个会骗人的指标。** 这是整个作品最核心的一句话：

> 失败率从 62.5% 降到 50%，看着是 12.5 个点的改善。
> 但摊开看：只有 **1 个任务**被真正修好，**1 个**被弄坏了，
> **4 个**从「每次都失败」变成了「一半概率失败」。
> 抛硬币任务从 1 个涨到 4 个 —— 失败率降了，不确定性反而涨了。

确定的问题可以排期修，随机的问题没法排期，只能被反复重新发现。
所以「一半过一次不过」只能拿「变好了，但不稳」，拿不到「修好了」。

**③ 换个死法不叫修复。** v2 的 4 个换死法任务里，有 3 个的新死因都是「说了却没做」——
原来「只问不做」用户一眼能看出没办成，「说了却没做」用户会以为办成了。
这比失败率的任何数字都更值得报告，而失败率对它完全隐形。

**④ 机器判不准时，交给人。** 规则式归因给出的是证据强度，不是正确概率。
置信度 0.70 和 0.85 的诊断在报告里长得一样，但前者可能只是证据刚够写下来。
所以证据不足的进复核队列，人签字才算数。

**⑤ 单轮测试漏掉的不是病，是样本。** 这是第二句核心话：

> 多轮里有一类轮次，用户输入里根本没有订单号——「就按你说的办」「这个不要了」。
> 单轮测试给它一条孤立输入，不是会做错，是**无从下手**。
> 所以只做单轮测试的团队，漏掉的第一样东西不是某个 bug，是**这条用例压根造不出来**。

再往下一层才是跨轮病：纠正被忽略、跨轮丢失、重复副作用。
它们更阴——**单独测会通过**。绿灯是真的，只是不该亮。

**⑥ 改 prompt 这件事，缺的不是编辑器是出处。** 诊断的终点不是「你有 4 类病」，
而是「下一版该怎么写」。但从「诊断结论」到「真正落进 prompt 的那一行」之间，
通常是断的：人拿到一段规则草稿，打开编辑器粘贴，改完就忘了为什么这么改，
下次复发时也查不到是哪条证据让它进来的。

会诊室把这一段接上：**每一条新增规则都带来源标记** `[来源:pattern:over_escalation]`。
这一行刻意冗余——prompt 给模型看，这一行给人看。

### 完成度（对应评分项 40 分）

十二个能力，全部可点、可查、可复算：

| 能力 | 产出 |
|---|---|
| 分叉点定位 | 第一条走岔的决策，逐决策对齐 |
| 失败模式归纳 | 11 类性质，碎片合并，不允许「8 类里 6 类各 1 次」 |
| 最小复现 | 11 步压到 4 步，标注每步的角色（根因 / 必需上下文 / 后果 / 可删） |
| 回归验收 | 改完 prompt 传新轨迹，判五态（已修复 / 不稳定 / 仍存在 / 变成别的病 / 未覆盖） |
| 规则草稿 | 可直接粘贴进 system prompt 的那一条 |
| 规则评分器 | 7 项，0/0.5/1 三档，判不了就 skip 不给分 |
| 通用接入 | OTLP / OpenAI / LangSmith / 本项目格式，自动识别 |
| 逐任务实验对账 | 8 态判定 + 单版本稳定性 + 病种迁移 |
| 人工复核 | 4 个信号筛队列，确认 / 改判 / 驳回分别计量 |
| **多轮会话诊断** | 真跑会话（共享世界状态 + 累积历史），三类跨轮病 + 漏检率 |
| **SDK 实时上报** | 零依赖、`wrap()` 一次埋点、SSE 推送、现场回灌真实轨迹 |
| **Prompt 版本管理** | 血缘 + 出处 + 句级 diff + 从诊断生成带来源的草稿 |

**工程侧**：86 个单元测试、55 项真实浏览器端到端断言（含真点一遍
「确认 → 改判 → 撤销」的签字流程、真点一次 diff、真回放一次实时流）、
九个页面在 390px 手机上零横向溢出。

### 使用体验（对应评分项 25 分）

**打开就能用，不用注册、不用配 key。** 所有分析都基于已采集的轨迹快照，
服务启动不调用任何模型 API —— 演示是确定的、免费的、可复现的。

**它诚实地标注自己的边界。** 界面上每一处都写清楚：

- 最小复现是**结构推断**，`verified_by_replay` 永远是 `false`，每处都标注「未经重放验证」
- 导入的 OTLP / LangSmith 轨迹只知「工具有没有报错」，不知「任务有没有成」，
  所以任务级归因自动降级为「未判定」—— 不把不确定冒充成通过
- 置信度是规则的证据强度，不是统计概率
- 48 条样本，占比只应看趋势，不应当结论

**任意两条轨迹可并排对比**（`/api/compare`），不限同任务、不限结局。

**现场接诊**：把你自己的轨迹拖进来，即时得到诊断 + 最小复现 + 评分，
不落库、不外传 —— 只有你主动点「存进回归集」才会写盘。

**接入只要两行。** 实时流那一页给出的不是文档链接，是能直接粘的代码：

```js
import { Clinic } from "https://agent-clinic.app.workbuddy.host/sdk/agent-clinic.js?sharecode=HRSKWOV2YB";
const tools = clinic.wrap({ get_order, refund_order });
```

（`endpoint` 同样要带 `?sharecode=HRSKWOV2YB` —— 演示站用分享码保护，两处都带才放行。）

`wrap()` 比 `step()` 重要，因为实际接入时人只会用前者。SDK 绝不阻塞业务：
上报失败就进队列，队列满了丢最旧的，`keepalive` 让页面关掉也能发出去。

**多轮会话页的两种成功率并排摆。** 同一个 3 轮会话挂 1 轮，按轮算是 67%，
按会话算是 0 —— 用户真实的感受是后者。差的那一截就是「聊到一半崩掉」。

## 四、60 秒自证清单

评委/读者打开链接后，三个动作可以验证上面所有说法：

1. **打开「实验对比」** —— 会直接读到那句话（修好 1 / 弄坏 1 / 4 个变抛硬币）。
   点第一行（T04「弄坏了」）→ 点「对比这两版差在哪一步」，
   屏幕上会并排显示 v1 的 `refund_order` 与 v2 的 `escalate`，以及两版的最终答复原文。
2. **打开「复核队列」** —— 27 条诊断只进来 7 条。随便点一条「确认机器判定」，
   分布表不动；再点「改判为另一种病」并填一个理由，分布表立刻变。
   改判不填理由会被服务端拒绝（400）。
3. **打开「现场接诊」** —— 点「OpenAI」载入样例，再点「开始会诊」，
   30 秒内走完「导入 → 归因 → 最小复现 → 评分」全链路。
4. **打开「多轮会话」** —— 顶部第一个数字不是失败率，是「几轮单轮根本造不出样本」。
   点任意一场进详情，每一轮都标着「独立 / 需要历史 / 被历史害了」。
5. **打开「Prompt 版本」** —— 点「两版对比」，diff 是按**句**切的：v1 是一整段、
   v2 是五条规则，按行只会显示「6 行全改」。再点「从诊断生成下一版」，
   生成的草稿每段前面都挂着它是被哪条证据写进去的。
6. **打开「实时流」** —— 点「回放真实轨迹」，事件一条条滚进来；
   这一页的流是真的 SSE，不是前端假动画。

## 五、社媒文案

### 版本 A · 小红书 / 公众号（长）

```
我把 Agent 的失败率从 62.5% 降到 50%，然后发现自己做了一件蠢事

改完 prompt 跑了一批轨迹，失败率降了 12.5 个百分点，本来挺开心。

但把同一批任务逐条摊开之后，真实情况是这样的：

· 真正修好的只有 1 个任务
· 弄坏了 1 个本来稳定通过的任务
· 4 个任务从「每次都失败」变成了「一半概率失败」

失败率降了，不确定性反而涨了。

更离谱的是，那 4 个任务的死因都变了：原来「只问不做」（用户一眼能看出没办成），
现在变成「说了却没做」（用户会以为办成了）—— 失败率一模一样，性质更糟。

这件事让我意识到，失败率这个指标是会骗人的：确定的问题能排期修，
随机的问题只能被反复重新发现，但两者在总分里长得一模一样。

所以我做了「Agent 会诊室」：不做又一个 trace 查看器，只做归因这件事。

它能回答三个问题：
1. 这次的失败，和上次那次，是同一个病吗？
2. 改完 prompt，是修好了，还是换了个死法？
3. 这份诊断里，哪几条能直接拿去改线上，哪几条只是猜的？

它还做了两件 LangSmith 们不做的事：

把 Agent 放进多轮会话里真跑（各轮共享世界状态和对话历史），结果发现
32 个轮次里有 12 个，单轮测试连样本都造不出来——用户说「就按你说的办」，
输入里根本没有订单号，孤立的一条输入不是会做错，是无从下手。

以及：诊断的终点不是「你有 4 类病」，是「下一版 prompt 怎么写」。
每一条新增规则都挂着它的出处（哪条证据让它进来的），两版之间按句对比，
草稿版的失败率留空——没测过和测了全挂，是两件事。

最后一问是认真的：规则归因给出的是「证据强度」不是「正确概率」，
所以证据不足的诊断会进复核队列，人签字才算数。

在线体验（打开即用，不用注册）：见评论区
```
