# 多轮会话与版本管理

这份文档讲两件事：为什么多轮不能用单轮的办法测，以及为什么改 prompt 这件事必须留下出处。

---

## 一、多轮会话

### 1.1 「多轮」这个词的全部含义

一个常见的实现方式是：把三条单轮轨迹贴上同一个 session id，就算支持多轮了。

那不是多轮。多轮有两个不可省略的物理事实：

1. **世界状态共享。** 第 1 轮退掉的钱，第 2 轮查出来必须是已退。否则第 2 轮的 `refund_order` 会成功，而现实中它会撞上余额上限。
2. **对话历史累积。** 第 2 轮用户不再重复订单号，Agent 只有靠历史才知道他在说哪个订单。

本项目里这两点落在 `runSession()` 的两个变量上：

```js
const tools = makeTools(clone(world));        // 整场会话只建一次
const messages = [{ role: "system", ... }];   // 一路传下去，每轮追加
```

少任何一个，「多轮」就退化成「编号不同的单轮」。

### 1.2 三类跨轮病

只有多轮才会出现、单轮无论怎么测都测不出来的三类问题：

| 病种 | 判据 | 硬证据 |
|---|---|---|
| 纠正被忽略 | 本轮出现改口标记（「不对」「我说的是」）且给出新标识符，但本轮所有调用都没触及新目标 | 新/旧标识符都来自用户原话或调用参数 |
| 跨轮丢失 | 本轮用户没给标识符，历史给过，而 Agent 在轮末重新索要，且整轮没有做出任何工具调用 | 历史原话 + 终答原文 |
| 重复副作用 | 同一写操作（工具 + 标识参数）在两个不同轮次成功执行，且本轮用户没有「再/还/剩下的」这类追加要求 | 两次调用的参数 |

三条判据都只用**可见证据**：哪一轮的哪句话、哪次调用的哪个参数。

**不做的事**：不打「语义连贯性」分。那种判断没法被反驳，也就没法被修——一个人说「我觉得这里不连贯」，另一个人无法证伪，最后只能靠谁声音大。

### 1.3 什么时候会算错

这是必须写在文档里的部分。三类检测都有明确的失效边界：

**纠正被忽略**

- 用户改口但没给新标识符（「不对，你搞错了」）→ 不报。因为无法断言「应该改成什么」，报了也只是抱怨。
- 用户说的是另一个订单但语气不含改口标记 → 漏报。`_CORRECTION` 是一组语言标记，不是语义理解。措辞超出集合就会漏。
- 严重度分两档：写操作落在旧目标 = 3，只有查询 = 2。因为「查错了」还没造成损害。

**跨轮丢失**

- Agent 已经查完东西、末尾顺手确认一句「请确认订单号 A1033 对吗」→ 不报。那是谨慎，不是遗忘。判据里专门有一条 `acted` 检查。
- Agent 真的忘了，但追问措辞不在 `_ASK_AGAIN` 里（比如「您说的是哪个？」）→ 漏报。

**重复副作用**

- 用户说了「剩下的也退」→ 不报。重复是被要求的。
- 两次金额不同但订单相同 → 仍算重复。副作用身份只看「工具 + 标识参数」，不看金额：分两次退不同金额仍是同一个对象上的同一次副作用。
- `escalate` 重复会报，`get_order` 重复不会——查十次只是浪费，写两次就是事故。

### 1.4 单轮测试的漏检率

这一页最重要的数字是 `blind_spot_rate`：

```
盲区轮次 = 「被历史害了」且失败的轮次
漏检率   = 盲区轮次 / 总失败轮次
```

为什么 `needs_history` 不算盲区：这类轮次单独测会**报错**（信息不足，Agent 追问或乱猜），测试能发现它有问题。而 `harmed_by_history` 单独测会**通过**——单轮测试给它一个假绿灯。

这就是「只做单轮测试」真正的代价：不是漏掉了一些样本，而是那部分样本会给出错误结论。

**局限**：盲区率的样本量比单轮更小（一个会话只有 2~4 轮）。它回答的是「哪一类交互会出问题」，不是「出问题的概率」。界面上原样标注了这一点。

### 1.5 两种算法，两个数字

```
按轮算   = 通过的轮次 / 总轮次
按会话算 = 每一轮都通过的会话 / 总会话
```

差多少，就是「聊到一半崩掉」的比例。一场 3 轮会话挂 1 轮，按轮算是 67%，按会话算是 0——而用户真实的感受是后者。

只报按轮的成功率，会把这个问题整个藏起来。

## 二、Prompt 版本管理

### 2.1 为什么诊断工具要管 prompt 版本

诊断的终点不是「你这里有 4 类病」，而是「下一版该怎么写」。

如果版本管理只做成一个文本框，那这条路就断在最后一步：用户拿到规则草稿，得自己粘贴、自己记住改了什么、自己对比效果。诊断给出的证据、复核写下的理由、规则草稿描述的对策，到「真正落进 prompt 的那一行」之间没有任何连接。

本项目的做法：**每条新增规则必须带来源**。

```
[来源:pattern:over_escalation] 过度转人工（15 次）
- 以下情形必须直接办理，不得转人工：在受理期限内、金额未超上限、订单归属校验通过。
```

那个 `[来源:...]` 标记是刻意的冗余——prompt 是给模型看的，但这一行是给人看的。等版本验证通过、准备定稿时删掉即可，判断已经做完了。

来源有三类：失败模式（`pattern`）、人工复核改判（`review`）、跨轮场景（`session`）。没有来源的改动也能做，但会被标成 `manual`，界面上与「有据可查」的改动分开显示。

### 2.2 不改基线版

`compose_patch()` 只在基线正文的末尾追加，不动任何已有规则。

理由很硬：如果同时改了旧规则和加了新规则，那么这一版跑出来变好或变坏，你永远说不清是新规则起的作用，还是旧规则被改坏/改好了。一次只动一个变量，是能得出因果结论的前提。

### 2.3 草稿的失败率是空的，不是 0%

新生成的版本 `status: "draft"`，没有跑过任何轨迹，`fail_rate` 返回 `None`，界面上显示「未测」。

「没测过」和「测了全挂」是两件事。把前者显示成 0% 会让人以为它是最好的版本，直接拿去上线。

### 2.4 为什么 diff 按句对齐，不按行

v1 的正文是一整段话，v2 是五条编号规则。按行对齐只会得到「6 行全部被替换」——读者看不出「到底加了哪几条规矩」。

按句对齐才能显示成「3 句变成 7 句：1 句相同、2 句改写、4 句新增」。而那个 1→3 就是这次修复本身。

切分只认 `。！？` 与换行，**不拆分号**：分号在中文明细里是并列项，拆开会让一条规则碎成几段，反而读不出「这是一条规矩」。

每行都带原文行号，句级对齐提供精度，行号负责让人能回到原文定位。

### 2.5 不做的事：自动优化 prompt

这个模块不声称能自动生成「最优 prompt」。

文本质量不是一个规则引擎能保证的事。规则能做的只有两件：把「该写什么」摆出来（规则草稿），把「为什么写」摆出来（来源与证据）。剩下的编辑动作留给人。

声称能自动优化，结果是输出不可追责——出了问题没人能说清这条规则是从哪来的。

## 三、两个模块的连接

串起来是一条完整的闭环：

```
诊断（哪里坏了）
  → 规则草稿（该写什么）
  → 生成草稿版本（写进去，带来源）
  → 跑一批新轨迹（单轮采集台 / 多轮采集台 / SDK 上报）
  → 实验对比（逐任务看翻转）
  → 回归验收（原来的病还在不在）
  → 复核队列（机器判不准的人来签字）
```

每一步的产物都是下一步的输入，且每一步都留下可追溯的记录。

这个闭环里唯一没有自动化的是「编辑」——那是刻意的。
