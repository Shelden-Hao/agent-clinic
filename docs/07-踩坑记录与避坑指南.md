# 踩坑记录与避坑指南

这份文档只记一件事：**这次真的被咬到的地方**，以及下次怎么绕开。

每条都按同一个格式写——症状、根因、修法、怎么避免。凡是"当时觉得没问题、事后发现是错的"，
都单独标出来，因为那类坑最贵：它不会报错，只会让你得出一个看起来很漂亮的错误结论。

读法建议：赶时间就直接看最后一节的速查表。要接手这个项目，请按顺序读完全文。

---

## 一、协议层：接上了，但看不见

### 1.1 单步事件必须嵌套在 `step` 字段里

| | |
|---|---|
| **症状** | 上报接口返回 `{"ok":true}`，服务端照常广播，但页面永远显示「0 步 / 等待第一步…」 |
| **根因** | JS SDK 发的是 `{"type":"step","run_id":"...","step":{...}}`，Python 客户端第一版发成了扁平结构。前端读 `ev.step` 拿到 `undefined` |
| **修法** | `real_eval/clinic_client.py` 里统一包一层 `{"type":"step","step":{...}}` |
| **怎么避免** | 前端消费的字段路径，就是协议的**硬约束**。换语言重写客户端时，第一件事是拿浏览器网络面板里的一条真实请求当样本，逐字段比对，不要照着文档"理解"一遍再写 |

这个坑的恶劣之处在于**全链路无一处报错**：服务端收得下、存得住、广播得出去，客户端拿到 200。
唯一出错的地方是浏览器里的 `undefined`，而它不会抛异常。接第三方 SDK 时，"接口成功"和"界面正确"是两件事。

### 1.2 endpoint 带查询串时，路径会被吃掉

| | |
|---|---|
| **症状** | 线上分享链接（`https://xxx/?sharecode=XXXX`）上报静默 403，本地 `http://127.0.0.1:3131` 一切正常 |
| **根因** | 老代码 `endpoint + "/api/stream/step"` 直接字符串拼接，拼出 `host?sharecode=X/api/stream/step`。查询串后面的内容全成了参数值，路径根本不存在 |
| **修法** | `sdk/agent-clinic.js` 新增 `_url(path)`：先把 `?` 切开，路径插在查询串**之前**，并削掉根地址尾部斜杠 |
| **怎么避免** | 只要用户可以填 endpoint，就必须假设它带查询串、带尾斜杠、带子路径。拼接 URL 用 `new URL(path, base)` 或 `_url()` 这类显式函数，别用 `+` |

### 1.3 本地请求必须绕开系统代理

| | |
|---|---|
| **症状** | `curl http://127.0.0.1:8788/v1/models` 返回 502，网关日志里什么都没有 |
| **根因** | 环境里的 `HTTP_PROXY` 指向一个本地代理，`127.0.0.1` 的请求也被它接管了 |
| **修法** | 本地/内网请求加 `--noproxy '*'`；Python 侧用 `urllib.request.build_opener(ProxyHandler({}))` 显式禁用代理 |
| **怎么避免** | 写任何本地联调脚本，默认就带 `--noproxy '*'`。等它 502 了再查代理，会把时间全花在错误的层上 |

## 二、判定层：假绿灯比报错危险

这一节是整份文档最该被记住的部分。它们的共同点是：**系统没坏，结论坏了。**

### 2.1 只有 `forbid` 没有 `must` 的轮次，什么都不做也会判通过

| | |
|---|---|
| **症状** | 7 个场景跑出 5/7 通过，看着还行 |
| **根因** | 判定只看"该调用的动作调了吗 / 不该调用的调了吗"。如果某轮只有 `forbid` 规则，Agent 全程一动不动同样满足条件 |
| **修法** | `run_eval.py` 增加"未覆盖"态：若某轮只有 `forbid`、没有 `must`，且 Agent 一次工具都没调，判**未覆盖**，不算通过 |
| **怎么避免** | 判定函数里必须存在一个"什么都没做"的分支，而且它是失败分支。写判定时先问：**最懒的 Agent 要怎样才能骗过这条规则？** |

### 2.2 存盘的 `expect` 不会自动跟随 `scenarios.json`

| | |
|---|---|
| **症状** | 修好了 S02 的判定口径，重跑页面数字**一点没变** |
| **根因** | 会话 JSON 在采集时把当时的 `expect` 一起存盘了（这是对的，轨迹要可复现），服务端读的是存盘值。改 `scenarios.json` 对历史数据无效 |
| **修法** | 写 `tools/rejudge_sessions.py` 做**最小重判**：只动 S02 第 2 轮这一处，其余 7 个期望动作原样保留 |
| **怎么避免** | "判定口径"和"轨迹数据"是两个版本维度。改口径后必须显式重判或重采，不能指望自动生效。重判脚本要写清"我只改了哪一处、为什么其他没动" |

### 2.3 多轮里「已经办过了」被当成失败

| | |
|---|---|
| **症状** | S02 第 2 轮被标红，但 Agent 的回答其实是正确的 |
| **根因** | 期望动作写的是 `refund`。而第 1 轮已经越权退了 299，正好等于应退上限；第 2 轮正确的做法是"已经退过了，不再退"。按 `refund` 判，正确行为被判成失败 |
| **修法** | 新增 `ensure_refunded` 口径：这一轮结束时，这笔钱必须是退过的，前序轮次退过的也算（前序累计 + 本轮增量，对 `max_amount`） |
| **怎么避免** | **假阴性比假阳性更危险**：假绿灯只是让你少发现一个 bug，假红灯会让你去"修"一段本来就是对的逻辑。多轮场景的期望必须写成"轮末应满足的状态"，而不是"本轮应发生的动作" |

重判后失败轮 21 → 17。

### 2.4 `evidence` 是字符串，不能按字符切片

| | |
|---|---|
| **症状** | 拉回来的诊断证据全是单个汉字，一条一条断在奇怪的地方 |
| **根因** | `evidence` 是已经拼好的自然语言句子，代码里当成数组用了 `slice(0, n)` |
| **修法** | 按字符串处理，需要截断用 `slice(0, n) + "…"` 或整条展示 |
| **怎么避免** | 跨服务取字段前先 `console.log` 一次类型。字段名像数组不代表是数组 |

### 2.5 同一 `run_id` 有多次试验时，只取最新

| | |
|---|---|
| **症状** | 报告里的诊断结论和页面上看到的对不上 |
| **根因** | 同一个场景重跑过几次，轨迹流里有多条同 `run_id` 记录，取到了旧的那条 |
| **修法** | `report.py` 按 `run_id` 去重，保留最新一条 |
| **怎么避免** | 事件流天然是 append-only 的，读取端必须自己定义"谁是当前版本"。默认取第一条是错的 |

## 三、数据层

### 3.1 十二轮"连样本都造不出来"，这不是 bug，是结论

16 场会话 / 32 轮里，有 12 轮**单轮决策根本造不出可判定的样本**——用户第 2 轮只说"那笔也退了吧"，
不给订单号。这类轮次放进"成功率"分母会污染结论。

**处理方式**：主结论卡改用 `needs_history` 轮数（12/32）当主数字，漏检率为 0 时不再拿它当卖点。
`web/src/views/Sessions.vue` 上写明了"不漏样本和抓跨轮病是两件事，前者先发生"。

**怎么避免**：分母不干净的时候，先修分母，别急着算比率。

### 3.2 统计口径要现算，不要凭印象

本次核对过的真实数字（重跑一遍就能复现）：

```bash
node -e "const d=require('./data/sessions.json');const ss=d.sessions||d;..."
```

- 16 场会话 / 32 轮
- 轮成功率 15/32 = 46.9%
- 整场全对 2/16 = 12.5%
- 第 1 轮失败率 81.3%（13/16 失败），第 2 轮失败率 25%（4/16 失败）

**失败高度集中在第 1 轮**——第 1 轮的槽位抽取/上下文建立才是瓶颈，第 2 轮有历史兜着反而更好过。
这个结论如果靠印象写，会写成完全相反的"多轮更难"。

### 3.3 `data/regression.json` 不是 e2e 残留，别删

清理时差点把它当测试垃圾删掉。它是 commit `33eaed6` 引入的**真实回归集**，`data/` 下其他文件也各有用途，
不是构建产物。

**怎么避免**：删 `data/` 下任何文件前先 `git log --follow <file>`，看它是哪次提交、为什么来的。

## 四、环境层（Windows）

### 4.1 pip 装依赖能装到天荒地老，原因有三个

| 项 | 情况 |
|---|---|
| **症状** | `pip install -r requirements.txt` 跑了几小时没有任何进展 |
| **根因** | ① 没配国内镜像；② 继承了系统代理，pip 在代理上超时重试；③ `torch` 这类重依赖在拉 GB 级 wheel |
| **修法** | 生成 `requirements-eval.txt` 去掉 `torch` / `sentence-transformers`（本次评测用不到），配清华源，清空代理变量 → **111 个包 4 分 46 秒装完** |
| **怎么避免** | 装依赖前先看它是不是**真的需要**。`torch` 在本项目里是 `embedder.py` 的函数内懒加载，不调检索路径就根本不会 import。删掉它不影响任何被测行为，省下的却是绝大部分时间 |

### 4.2 `pip.ini` 里有中文注释会直接报错

| | |
|---|---|
| **症状** | `invalid cp936 characters`，连 pip 都起不来 |
| **根因** | pip 配置文件按系统编码（cp936）读，注释里的中文炸了 |
| **修法** | `pip.ini` 只写纯 ASCII |

### 4.3 这个环境里别指望 PowerShell

`Write-Output`、`Get-Date` 都可能返回空输出（exit 0 但无 stdout），后台任务更是经常整体失败。
`Add-Type`、`New-Object -ComObject Shell.Application`、从 bash 里调 `powershell.exe` 全部会被安全策略拦。

**结论**：优先用 Bash / Python 干活。需要写文件核对时也走 Python，不要绕着 PowerShell 试。

### 4.4 `rm` 在本机不是真的删

`rm` 被包成了走回收站的 shim。删完 `df` 不变、删回收站里的东西会死循环失败。
真要释放空间用 `/usr/bin/rm -rf <POSIX 路径>`，并且**路径必须是 POSIX 风格**——传 `$APPDATA` 展开出的
`C:\Users\...` 反斜杠绝对路径，shim 会把 cwd 前缀拼上去，变成畸形路径后两种删除方式一起失败。

## 五、模型层：便宜的不一定差，贵的不一定行

按"优先消耗最少额度"的原则逐级试，结果很反直觉：

| 档位 | 模型 | 额度 | 结构化命令解析 | 结论 |
|---|---|---|---|---|
| 1 | `hy3` | x0.00 | 6/6 轮 `No commands parsed` | 不可用 |
| 2 | `glm-5.3-flash` | x0.08 | 正常 | **采用** |
| 3 | `deepseek-v4.1-flash` | x0.11 | 2/2 轮解析失败 | 更贵且更差 |

**这不是排序问题，是能力门槛问题**：框架要求模型输出严格格式的命令 JSON，免费档做不到。
而贵 37% 的 `deepseek-v4.1-flash` 在这个格式上反而更差——**升级不保证变好，只保证变贵**。

**怎么避免**：选模型时先定"最小可用能力"的判据（能不能产出可解析的结构化输出），
按额度从低到高试，一档过了就停。别先入为主认为贵的更强。

## 六、设计层：真实项目才暴露的问题

把会诊室接到真实 Agent（`intelligent_customer_service`）上跑出 5/7，暴露出真正该修的东西：

### 6.1 11 类病种的规则依赖了"自造动作名"

| 自造世界 | 真实 Agent |
|---|---|
| `refund_order` / `transfer_to_human` / `get_order` | `action_ask_order_id` / `action_check_postsale_eligible` / `utter_ask_postsale_type` |

规则是照着左边写的。真实动作名一换，规则全部沉默，落到「未归类 置信 0.0」——
**诊断没崩、没报错，但输出是空的**。7 轮里 6 轮如此。

**要补的不是模型，是"工具语义 + 流程阶段"的映射层**：把 `action_ask_order_id` 归到
"追问槽位"语义，把 `action_check_postsale_eligible` 归到"资格校验"语义，病种规则跑在语义上而不是动作名上。
换模型解决不了这个问题。

### 6.2 单步判定会把"流程走歪但没到终点"判成通过

真实客服是跨轮多步的。只看"某个动作这一次有没有被调用"，R02 / R04 都被判了通过，
但它们其实是"没做完就结束了"。判定要加"轮末状态"，不能只看单步动作。

### 6.3 结论

> 自造数据上的绿灯，不等于真实可用。

真实项目里最有价值的一条结论，反而是那个看起来很差的结果：R05 诊断「原地绕圈 置信 0.9」，
证据是连续 3 次以完全相同参数调用 `action_ask_order_id`，最小复现 1 步。
修法明确——要么修槽位抽取，要么给 collect 步骤加重试上限。**这类结论在自造数据上编不出来。**

## 七、速查表

接新项目 / 改判定逻辑前，过一遍这张表：

| # | 检查项 | 一句话 |
|---|---|---|
| 1 | 上报事件结构 | 换语言重写客户端，先拿一条真实请求当样本逐字段比对 |
| 2 | URL 拼接 | 假设 endpoint 带查询串、带尾斜杠、带子路径 |
| 3 | 本地请求 | 默认加 `--noproxy '*'` |
| 4 | 判定分支 | 必须有"什么都没做 = 失败"的分支 |
| 5 | 期望写法 | 写"轮末状态"，不写"本轮动作" |
| 6 | 口径变更 | 改判定口径后必须显式重判或重采，不会自动生效 |
| 7 | 字段类型 | 取跨服务字段前先确认类型，`evidence` 是字符串 |
| 8 | 事件去重 | append-only 流要自己定义"当前版本"，默认取最新 |
| 9 | 分母 | 分母不干净先修分母，别急着算比率 |
| 10 | 依赖 | 装之前先看是不是真需要（`torch` 常常不需要） |
| 11 | 删文件 | 删 `data/` 下文件前先 `git log --follow` |
| 12 | 模型 | 先定最小可用判据，按额度从低往高试，过了就停 |
| 13 | 动作名 | 病种规则跑在"语义"上，不跑在别人的动作名上 |
