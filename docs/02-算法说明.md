# 02 · 六个核心算法的原理与失效边界

这一层是项目的立论基础，所以每个算法都写清三件事：**怎么算、为什么这么算、什么时候会算错**。

---

## 一、首个出错决策定位（`diagnose.py`）

### 怎么算

七组规则各自扫描一遍轨迹，每条规则产出若干 `Finding(kind, step_index, evidence, severity)`：

| 规则 | 触发条件 | 产出性质 |
|---|---|---|
| `_detect_tool_errors` | 工具返回 `ok=False` | `bad_argument` / `tool_error` |
| `_detect_loop` | 连续 3 次完全相同参数调用 | `loop` |
| `_detect_hallucinated_fact` | 最终答复里的订单号/日期在观测中不存在 | `hallucinated_fact` |
| `_detect_escalation_missed` | 任务要求转人工，却调了退款 | `escalation_missed` |
| `_detect_task_level` | 任务要求的动作没发生 | `over_escalation` / `asked_instead_of_acted` / `promised_but_not_done` / `no_action` |
| `_detect_premature_answer` | 答复引用政策但没检索政策库 | `premature_answer` |
| `_detect_redundant_query` | 相同参数隔步重查 | `context_lost` |

然后：

```python
findings.sort(key=lambda f: (f.step_index, -f.severity))
root = findings[0]
```

### 为什么先比步号再比严重度

**早发生的小错往往才是根因，晚发生的致命错常常只是它的后果。**

举例：第 2 步参数传错 → 工具报错 → 第 3 步模型开始编造 → 最终答复幻觉。
按严重度排会指向最后的幻觉，但对用户的修复动作毫无帮助。
按步号排指向第 2 步，改一个参数，后面全好了。

这是「会诊」和「看日志」最本质的区别。

### 什么时候会算错

- **规则命中多项时只返回最早的那条**。如果两条独立的错在很靠前的位置同时发生，第二条会被压在 `findings` 里不显示为结论。
- **`_detect_hallucinated_fact` 只认结构化标识符**（订单号正则 `[A-Z]{1,3}\d{4,}`、日期）。模型自己算出来的金额不算幻觉 —— 那是合理推导。这个保守选择会漏掉「编造了一段政策描述」这类问题。
- **任务级规则强依赖 `expected`**。没有期望时这四类完全不工作，落进 `unknown`。

## 二、双路径对齐（`align.py`）

### 怎么算

把两条轨迹的决策序列转成 `signature` 序列，跑最长公共子序列（LCS），得到对齐表。未匹配的位置标为插入/删除。

**`signature` 刻意不含参数值**：

```python
def signature(self):
    keys = ",".join(sorted(self.args.keys()))
    return f"{self.tool}({keys})"     # get_order(order_id) 而不是 get_order(order_id="A1024")
```

### 为什么不含参数值

最小化会改写参数值。如果签名带值，同一决策在两条轨迹里长得不一样，对齐会全错。
签名要表达的是**结构**（做了什么类型的事），不是**内容**（对谁做的）。

分叉点判定：

1. 第一处「只在失败轨迹里出现的决策」
2. 如果没有，第一处「两边都有但参数不同」的决策
3. 如果还没有 → 返回 `None`，明确说明「问题不在做了什么，而在同样的动作拿到了不同结果」

### 什么时候会算错

- **步数差很大时 LCS 会选出奇怪的公共子序列**。两条 5 步 vs 15 步的轨迹，对齐结果可能把无关步骤配成一对。
- **`fork_at` 是「结构分叉点」，不是「因果根因」**。真正的根因是 `diagnose` 给的，两者常常一致，但不是必然一致。

## 三、因果链最小化（`minimize.py`）

### 怎么算

从诊断锚点出发，三步走：

```
1. 反向依赖：锚点用到的标识符（订单号/日期），在前面的哪一步观测里出现过？
   → 那一步标记 required_context，保留

2. 前向传播：锚点之后，哪些步骤消费了锚点产出的标识符？
   → 标记 consequence，保留（这是失败向下游扩散的可见证据）

3. 剩余步骤：
   产出从未被任何「保留步骤」消费 → droppable，附理由
```

依赖的**唯一硬证据是标识符**（`_ID` / `_DATE` 正则）。
不做语义相似度 —— 那会把「措辞相近」误判成「有依赖」。

### 为什么保守

判定顺序是「先证明必要，再证明可以删」。
只有能拿出「它的返回值从未进入任何保留步骤的参数」这条硬证据时，才允许标 `droppable`。
少删几步不影响可用性；删错一步，整个用例就失去复现价值。

### 什么时候会算错

- **依赖全靠正则识别的标识符**。如果工具参数里没有这类 ID（比如传的是自由文本 query），依赖链会断，最小化会过度保守（什么都留）。
- **`terminal_only` 是设计而非缺陷**。任务级失败压到 1 步，是因为它本来就没有出错的那一步。
- **不可重放**。这是结构推断，`verified_by_replay` 恒为 `false`。

## 四、失败模式聚类（`cluster.py`）

### 怎么算

每次失败生成一个签名：`(性质, 出错工具, 归一化后的证据文本)`。

归一化把具体值抹掉：

```python
re.compile(r"[A-Z]{1,3}\d{4,}")  →  "<订单>"
re.compile(r"\d+(?:\.\d+)?")     →  "<数值>"
```

任务级失败（`over_escalation` 等四类）的证据措辞会随工具名变化，但病是同一种 ——
用 `_CANON` 表统一成固定句式，避免同一类病被拆成好几条。

**碎片合并**：只有 1 条样本的签名会被合并成「零散异常」，理由写在报告里：
总量不足以归纳，不要基于单例下判断。

### 什么时候会算错

- **归一化太浅**。只抹掉了数字和订单号。同一类病如果用完全不同的句子描述，会被拆成多条。
- **`_CANON` 是硬编码的 5 条**。新增病种时如果忘了加，会被聚成碎片。

## 五、规则评分器（`evaluate.py`）

### 怎么算

7 个评分器，各自返回 `0 / 0.5 / 1` 或 `None`（跳过）。加权求和：

| 评分项 | 权重 | 判什么 |
|---|---|---|
| 任务完成 | 3.0 | 要求的动作是否发生 |
| 转人工策略 | 2.0 | 该转的转了、不该转的没转 |
| 参数卫生 | 1.5 | 工具调用有没有被拒 |
| 结论有据 | 1.5 | 答复里的标识符能否溯源 |
| 无空转 | 1.0 | 无连续重复调用 |
| 错误恢复 | 1.0 | 出错后有没有成功的重试 |
| 执行效率 | 0.5 | 步数与 token 在预算内 |

### 为什么只有三档、为什么权重差这么多

- **三档**：轨迹质量不是连续可微的，给 0.73 分是假装精确。
- **权重**：「省了 token 但没办成事」不该拿高分，所以任务完成 3.0、效率 0.5。
- **`None` 不等于 1.0**：没有发生工具错误时，`错误恢复` 返回 `None`（跳过），不是给满分。

### 什么时候会算错

- **`scope: tool_only` 的总分会天然偏高**。没有任务期望时最重的两项不参与打分，界面上必须标明。
- **`结论有据` 只查标识符**。一段凭空编造的政策描述，如果里面没有订单号/日期，这项照样满分。

## 六、回归验收（`regress.py`）

### 怎么算

对回归集里的每条 case，在给定轨迹里找 `task_id` 相同的所有轨迹（**不退回按 prompt 模糊匹配**），逐条诊断，按命中比例判定：

| 命中比例 | 判定 |
|---|---|
| 全部命中 | `present` 仍存在 |
| 部分命中 | `partial` 不稳定 |
| 全部不命中 + 全成功 | `fixed` 已修复 |
| 全部不命中 + 仍失败 | `changed` 变成了别的病 |
| 找不到同任务 | `uncovered` 未覆盖（不计入通过） |

### 为什么单独列出 partial 和 uncovered

**`partial`**：4 条里 1 条还坏着，说「修好了」是骗人，说「还坏着」也不准确。
它是一个概率问题，必须单独表达。

**`uncovered`**：没考和考过了是两件事。混进通过率里，就是用一个更小的分母换一个更好看的数字。

### 为什么 task_id 严格匹配

第一版写了「task_id 找不到就退回按 task_prompt 匹配」，
单测立刻抓出问题：两条不同任务的 prompt 恰好相同，于是「没考到」被伪装成「已修复」。

**prompt 撞了不代表同一个任务。** 现在有 `task_id` 就只按 `task_id` 对。

### 什么时候会算错

- **case 的 `kind` 变了但本质没变**。比如「过度转人工」被修成「只问不做」，判定是 `changed`，
  但对用户来说可能只是换了个失败方式，严重程度未必降低。
- **不验证 case 本身是否仍有效**。如果业务规则变了（比如退款期限从 7 天改成 15 天），
  旧 case 的期望可能已经过时，系统不会发现。
