# 03 · 接入指南：把你自己的轨迹放进来

接入层的能力边界，比它会解析什么更重要 —— 这份文档先讲后者，再讲前者。

---

## 一、四种格式，能力不同

| 格式 | 识别特征 | 能诊断什么 | 不能诊断什么 |
|---|---|---|---|
| `native` | 有 `run_id` + `steps` | 全部 11 类 | — |
| `openai` | 有 `messages` 数组 | 若带 `expected` 则全 11 类；否则只有工具层 | 任务级（需期望） |
| `otlp` | 有 `resourceSpans` | 只有工具层：报错、参数、空转、重复查询 | **任务是否完成，一律判定不了** |
| `langsmith` | 有 `run_type` / `child_runs` | 同 openai | 同 openai |

**「不能诊断」不是缺陷，是这些格式本身不携带这个信息。**
OTLP 和 LangSmith 记录的是「执行」，不是「业务结果」——
一个工具全绿的轨迹，用户可能依然没拿到退款。

系统遇到这种情形的处理：标 `success_known: false`，诊断结论为「未判定」。

## 二、最小字段要求

### native

```json
{
  "run_id": "my-001",
  "task_id": "T01",
  "task_prompt": "用户的原话",
  "expected": { "action": "refund" },
  "success": false,
  "steps": [
    { "i": 1, "kind": "tool_call", "tool": "get_order",
      "args": { "order_id": "A1024" }, "observation": { "paid": 899 }, "ok": true },
    { "i": 2, "kind": "final", "content": "需要我帮您确认吗？" }
  ]
}
```

必填：`run_id`、`steps`。
强烈建议补：`expected`（解锁任务级归因）、`task_prompt`（回归验收的兜底匹配）。

也可以传数组，或 `{"runs": [...]}`，或 JSONL（每行一条）。

### openai

```json
[{
  "run_id": "my-002",
  "expected": { "action": "refund" },
  "success": false,
  "messages": [
    { "role": "user", "content": "订单 A1024 要退款" },
    { "role": "assistant", "content": null,
      "tool_calls": [{ "id": "c1", "type": "function",
        "function": { "name": "get_order", "arguments": "{\"order_id\":\"A1024\"}" } }] },
    { "role": "tool", "tool_call_id": "c1", "content": "{\"paid\":899}" },
    { "role": "assistant", "content": "需要我帮您确认吗？" }
  ]
}]
```

解析规则：
- `assistant` + `tool_calls` → 一个 `tool_call` 步
- `role: tool` → 回填上一步的观测；内容里出现 error/missing/invalid 等词时判 `ok: false`
- 最后一条无 `tool_calls` 的 `assistant` 文本 → `final`
- 中间的 `assistant` 文本 → `plan`（不参与归因，只用于对齐）

### otlp

标准 OTLP traces JSON。属性按 GenAI 语义约定读取：

| 属性 | 用途 |
|---|---|
| `gen_ai.operation.name` | `execute_tool` → 工具步；`chat` → 规划步 |
| `gen_ai.tool.name` | 工具名 |
| `gen_ai.tool.call.arguments` | 参数（JSON 字符串） |
| `gen_ai.tool.call.result` | 观测 |
| `gen_ai.request.model` | 模型名 |
| `gen_ai.usage.input_tokens` / `output_tokens` | token |
| `status.code = STATUS_CODE_ERROR` | 判为失败步 |

按 `traceId` 分组、按 `startTimeUnixNano` 排序重建轨迹。

### langsmith

`{"runs": [...]}` 或裸数组，支持树形 `child_runs` 和扁平 `parent_run_id` 两种形态。

扁平数组必须能顺 `parent_run_id` 爬到根 —— 这是第一版的 bug：
没做爬根，每条 run 都自成一棵树，13 条本该是 3 条的轨迹。

`run.error` 表示**执行异常**，不表示「任务没办成」。
所以有 error 才判失败，没有 error 只说明「工具没报错」。

## 三、补上期望，解锁任务级归因

如果你的轨迹没有 `expected`，系统只能做工具层体检。补上之后会立刻解锁：

| 期望字段 | 含义 | 解锁的判定 |
|---|---|---|
| `action: "refund"` | 这个任务应当发起退款 | 过度转人工、只问不做、说了却没做、没有动作 |
| `action: "escalate"` | 这个任务应当转人工 | 该转人工没转 |

接入时可以按 `run_id` 或 `task_id` 批量指定：

```json
{
  "text": "...轨迹 JSON...",
  "format": "auto",
  "expectations": {
    "T01": { "action": "refund" },
    "T03": { "action": "escalate", "reason": "超过退款期限" }
  }
}
```

## 四、常见错误与排查

### 「无法识别格式」

系统认不出结构时会明确列出支持的格式，不会硬套。
最常踩的坑：

- 传的是 **LangSmith 的 API 响应包装**（`{"data": [...]}`），而不是 `runs` 数组 → 取出内层再传
- 传的是 **OTLP metrics / logs**，不是 traces → 换 `resourceSpans` 那份
- 传的是 **OpenAI 的单条 message**，不是 messages 数组 → 包一层 `{"messages": [...]}`

### 「解析成功但没有得到任何可用轨迹」

通常是结构对了但内容为空：
- OTLP 里没有任何可识别为工具调用的 span（可能只开了 llm span）
- LangSmith 的 `run_type` 全是 `chain`，没有 `tool`

### 「任务级归因不可用」

见上一节。这是导入轨迹最常见的能力落差，界面上会明确提示。

### 诊断全是「未判定」

三个可能：
1. 没有 `expected`（最常见）
2. 工具的失败没有被正确标记为 `ok: false`（比如工具报错但你的代码吞掉了异常，仍记 `ok: true`）
3. 轨迹确实成功

## 五、接入之后

`POST /api/intake` 是无状态的：解析完就返回，不落库。

想把某条失败钉成验收项：

1. 在接诊结果里展开那条轨迹 → 看「最小复现」
2. 点「存进回归集」→ 写入 `data/regression.json`
3. 改完 prompt 重跑一批 → 把新轨迹传进来 → 点「用这批上传的轨迹验收」

第 3 步的输出会告诉你：修好了几条、还在几条、变成了别的病几条、没覆盖几条。

## 六、接口清单

```
GET  /api/intake/formats        支持的格式与体积限制
GET  /api/intake/sample/{fmt}   从真实轨迹转出的样例（可直接回传测试）
POST /api/intake                解析 + 诊断，无状态
GET  /api/runs                  轨迹列表
GET  /api/runs/{id}             单条详情（含逐步标注与最小复现）
GET  /api/regression            回归集
POST /api/regression/add        存入用例
POST /api/regression/verify     验收
GET  /api/docs                  OpenAPI
```
