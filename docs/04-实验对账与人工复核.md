# 04 · 实验对账与人工复核

这两块解决的是同一个问题的两端：**你的结论从哪里来，凭什么能拿去改线上系统。**

---

## 一、为什么「失败率」这个指标不够

改完 prompt，跑一批轨迹，得到两行数字：

```
v1   24 条   15 失败   62.5%
v2   24 条   12 失败   50.0%
```

这看起来是一次成功的优化 —— 降了 12.5 个百分点。但如果把这批轨迹按任务摊开：

```
任务    v1      v2      发生了什么
T01    0/2  →  2/2     真修好了
T02    0/2  →  1/2     一半概率失败
T04    2/2  →  0/2     被弄坏了
T06    0/2  →  1/2     一半概率失败
T07    0/2  →  1/2     一半概率失败
T08    0/2  →  0/2     一直坏着
T10    0/2  →  1/2     一半概率失败
T12    0/2  →  0/2     一直坏着
其余    ——       ——      稳定不变
```

同一个 62.5% → 50%，内部的构成是：**修好 1 个、弄坏 1 个、把 4 个变成抛硬币**。

这三件事在总分里长得完全一样。这就是实验对账存在的全部理由。

### 1.1 「一半概率失败」为什么不能算修好

失败率上，`1/2` 和 `0/2` 只差 0.5。但性质上是两回事：

- `0/2` 是一个**确定的问题**。它每次都会复现，可以排期、可以定位、可以回归验证。
- `1/2` 是一个**概率问题**。它在本地复现不出来，过几天以「偶发」的名义被重新发现，
  然后第三次被重新发现。它不可排期。

把确定问题改造成概率问题，在失败率上是改善，在工程质量上是负债。
所以判定口径里，`1/2` 只能拿到「变好了，但不稳」，拿不到「修好了」。

这与回归验收里的 `partial` 是同一条原则的两次应用：
**时好时坏不算修好，它只是把一个确定的问题变成了一个概率问题。**

### 1.2 判定表

| 判定 | 条件 | 说明 |
|---|---|---|
| `fixed` 修好了 | 基线不全通过 → 现在全通过 | 唯一能说「修好了」的情形 |
| `regressed` 弄坏了 | 基线全通过 → 现在不全通过 | 哪怕只坏一条也是坏 |
| `flaky_improved` 变好了，但不稳 | 通过率上升，但仍未全通过 | 表面改善，实际是换成了抛硬币 |
| `worse` 更糟了 | 通过率下降，基线本来就不完美 | |
| `flaky` 一直是抛硬币 | 前后通过率相同且都不完美 | 看起来「没变化」，实际两次都在掷骰子 |
| `stable_ok` 本来就稳 | 两版都全通过 | |
| `stable_bad` 一直坏着 | 两版都全不通过 | |
| `missing` 缺对照 | 某一侧没有数据 | 不判定，不猜 |

### 1.3 单版本稳定性

除了跨版本比对，每个版本单独算一次稳定性分布：

```
稳定通过（全过） / 抛硬币（有成的有败的） / 稳定失败（全挂）
```

这一项**只看版本自己**，不跨版本比较。它的价值在于：抛硬币任务数变多，
说明系统的不确定性在上升 —— 这是失败率降下来也换不回来的东西。

本项目真实数据：

```
v1   稳定通过 4 / 抛硬币 1 / 稳定失败 7
v2   稳定通过 4 / 抛硬币 4 / 稳定失败 4
```

失败率降了 12.5 个点，抛硬币任务从 1 个涨到 4 个。

### 1.4 病种迁移：换个死法不叫修复

两个版本都失败，但失败的理由换了 —— 这类任务会被单独拎出来。

```
T05   说了却没做     →  过度转人工
T06   没有动作       →  说了却没做
T07   过度转人工     →  说了却没做
T10   只问不做       →  说了却没做
```

它既不是「修好」也不是「弄坏」，失败率完全看不见它。但性质可能变得更糟：

- 「只问不做」—— 用户一眼就能看出没办成，会追问。
- 「说了却没做」—— 用户会以为办成了，直到过几天才发现。

本项目 v2 里，**4 个换死法的任务中有 3 个换成了「说了却没做」**。
这是这版 prompt 最该被注意的一件事，而它在失败率上是完全隐形的。

### 1.5 从「哪个任务坏了」到「差在哪一步」

矩阵回答的是「谁坏了」，不回答「怎么坏的」。所以每一行都能点开，
把两版的轨迹**逐决策并排对齐**（复用同一套 LCS 对齐）。

以本项目 T04 为例 —— v1 稳定通过，v2 稳定失败，判定「弄坏了」：

```
v1 · T04-v1-1 · 成功                    v2 · T04-v2-1 · 过度转人工
get_order(order_id)              =      get_order(order_id)
get_user(user_id)                ◀      —
search_policy(query)             =      search_policy(query)
refund_order(order_id, amount…)  ◀      —
—                                ▶      get_user(user_id)
—                                ▶      escalate(summary)
「已全额退款 329 元」             =      「已为您转接人工客服，工单号 H9205」
```

分叉点定在**第一条两边不一致的行**（第 3 步），而不是「第一条只出现在右边的行」——
后者在 LCS 把中间某步对齐到前面时，会落到一个看起来不太像分叉的位置上。

**注意对齐只认决策签名**（工具名 + 参数键），不含参数值。所以「参数不同」
不会被标成分叉。这是刻意的：参数值会被最小化改写，签名才是结构。

### 1.6 什么时候会算错

- **每格样本极少**（本项目每任务每版本 2 条）。这里给的是**现象标签**，不是统计显著性结论。
  它够用来决定「先查哪个任务」，不够用来证明「某个改动有效」。
- **判定只看通过率方向，不看幅度是否「显著」**。样本这么少，做显著性检验是自欺欺人。
- **`missing` 不猜**。某一侧没有轨迹时不做判定，而不是把缺失当成通过或失败。
- **跨版本比对只取首尾两个版本**。中间版本被跳过 —— v1 → v2 → v3 时，
  不会告诉你 v2 → v3 单独发生了什么。

## 二、为什么要有复核队列

规则式归因有一个绕不过的问题：它输出的是**证据强度**，不是**正确概率**。

一条置信度 0.70 的诊断和一条 0.85 的诊断，在报告里长得一模一样：
都是一个病名、一句证据、一个步号。但前者很可能只是证据刚够写下来。

多数工具的处理方式是：不处理。所有诊断一律用同样的语气呈现，让人自己去分辨。
演示时零成本，真要据它改 prompt 时就是灾难 —— 你会照着一条猜出来的结论改线上系统。

### 2.1 进队列的四个信号

每个信号都对应一个具体的、可检查的怀疑理由，不是「感觉不太准」：

| 信号 | 触发条件 | 为什么可疑 |
|---|---|---|
| `low_confidence` | 置信度 ≤ 0.70 | 规则证据刚够，多一个字段的证据都没有 |
| `unclassified` | `kind == unknown` | 规则根本没认出来，写的是「未归类」而不是某个病 |
| `unstable_pair` | 同任务同版本下有成有败 | 这条轨迹代表不了该任务，单条归因失去代表性 |
| `expectation_missing` | 缺任务期望 | 任务级规则全部失效，只能判工具层 |

`unstable_pair` 需要特别说明：比较范围是**包括自己在内的整组轨迹**。
如果写成「其他同组轨迹结果不一致」，那组里只有一条失败一条成功时，
每条都会看到「其他人的结果是一致的」，信号永远不会触发。

### 2.2 筛选力度：为什么只收 26%

第一版我把「同一任务换个版本被判成另一种病」也算作进队信号，
结果 27 条失败里有 17 条要人签字（63%）。

**筛不动的队列等于没有队列。** 如果所有「有点意思」的疑点都触发进队，
它只是把列表换个排版又念了一遍，人的注意力不会被集中到真正需要看的地方。

所以分成两档：

- `signals` —— 这条诊断本身不可靠，**必须**进队
- `hints` —— 结论可能没错，但周围证据有矛盾，**顺便看一眼**

跨版本死因不同被降级成 `hints`，因为它本身不是疑点（改了 prompt 本来就该换病）。
而且 hint 会带出具体病名（「同一任务在别的版本上主要死因不同：『过度转人工』」），
一句抽象的「跨版本不同」没有任何信息量。

本项目的最终结果：**27 条失败 → 7 条进队（26%）**。

### 2.3 三种动作，分量不同

| 动作 | 作用 | 统计口径 |
|---|---|---|
| `confirm` 确认 | 机器判定成立 | **不改动任何分布**，只减待签字、加确认数 |
| `override` 改判 | 换成另一种病 | 原病种减一、新病种加一。**必须写理由** |
| `dismiss` 驳回 | 判为不算失败 | 原病种减一、**失败总数减一** |

两条刻意的约束：

**确认不改分布。** 签字确认不是一次「动作」，它是「什么都没发生」。
如果确认也让数字动，那「机器判定的分布」和「人工确认的分布」就再也分不开了。

**改判必须写理由。** 它是唯一会改写结论的动作。
三个月后如果有人问「当初为什么把这条从『没有动作』改成『上下文丢失』」，
记录里必须有答案。服务端强制校验，不是前端提醒。

### 2.4 记录里存了什么

```json
{
  "action": "override",
  "kind": "context_lost",
  "note": "第 2 步重复询问了用户已经给过的订单号",
  "reviewer": "值班医师",
  "at": "2026-10-24T15:44:12+08:00",
  "original_kind": "no_action",
  "original_confidence": 0.7
}
```

`original_kind` 和 `original_confidence` 是**落盘时补上的**，不是人填的。

理由：如果只存「改成了什么」，三个月后病种表改了、规则改了，
这条记录就再也读不懂了 —— 你不知道它当初是从什么改过来的。
存原判，记录才能自证。

### 2.5 什么时候会算错

- **队列只覆盖「失败诊断」**。成功的轨迹不进队列 —— 但成功也可能被误判为成功
  （尤其导入的轨迹缺任务期望时）。这一块目前没有复核机制。
- **置信度阈值是拍出来的**（0.70 / 0.75 / 0.80 / 0.85 都是规则里写死的档位，不是连续值）。
  调阈值会直接改变队列大小，没有自适应机制。
- **复核是单机单文件**（`data/reviews.json`），没有多用户、没有并发锁、没有审计链。
  它够用在「一个人看结论」，不够用在「一个团队追责」。
- **复核不改变轨迹本身**。驳回一条诊断不会让那次失败消失，
  它只是把「这是一次归因失败」和「这是一次任务失败」分开记。

## 三、这两块为什么必须一起做

实验对账回答的是：**这次改动到底改变了什么。**
复核队列回答的是：**我凭什么相信这个结论。**

少了前者，你只能看到总分，而总分会骗你 ——
本项目里它把「弄坏 1 个」和「4 个变抛硬币」全都藏进了 12.5 个百分点的改善里。

少了后者，你的报告里每一条诊断都以同样的语气呈现，
读者无法区分「证据确凿」和「证据刚够」——
而这恰恰是规则式归因最大的软肋。

两者共用的原则只有一条：**不确定就说不知道，不要用确定的语气说不确定的话。**
